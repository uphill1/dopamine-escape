## Commands

Package manager is **pnpm** (see `packageManager` in package.json). Do not use npm/yarn.

- `pnpm dev` — start dev server at http://localhost:3000
- `pnpm build` — production build
- `pnpm start` — run production build
- `pnpm lint` — ESLint (flat config)
- `pnpm exec tsc --noEmit` — type-check (no separate `typecheck` script defined)
- `pnpm dlx shadcn@latest add <component>` — add a new shadcn/ui component into `components/ui/`

There is no test runner configured in this repo.

## Architecture

**Stack**: Next.js 15 (App Router, pinned — `create-next-app`/shadcn tooling defaults to Next 16, so keep `next` and `eslint-config-next` on the `15.x` line deliberately), TypeScript, Tailwind CSS v4, shadcn/ui, Supabase.

### shadcn/ui runs on Base UI, not Radix

`components.json` uses style `base-nova`. Components in `components/ui/` are built on `@base-ui/react`, **not** `@radix-ui/react-*`. The practical consequence: Base UI's polymorphic components use a **`render` prop**, not Radix's `asChild`:

```tsx
// wrong (Radix pattern)
<Button asChild><a href="...">Link</a></Button>

// correct (Base UI pattern)
<Button render={<a href="..." />}>Link</Button>
```

This applies to `Button`, `DropdownMenuTrigger`, and any other primitive from `@base-ui/react` re-exported through `components/ui/*`. When adding new shadcn components, check the generated file for `render`/`Props` typing before assuming Radix conventions.

### Dark mode

Dark mode is the default theme, wired through `next-themes`:
- `components/theme-provider.tsx` wraps `next-themes`' `ThemeProvider`.
- `app/layout.tsx` renders it with `attribute="class" defaultTheme="dark" enableSystem`, and the `<html>` tag has `suppressHydrationWarning` (required by next-themes to avoid SSR/client class mismatch warnings).
- `components/mode-toggle.tsx` is the light/dark/system switcher, using the `DropdownMenu*` primitives above.
- Theme tokens (light/dark CSS variables) live in `app/globals.css` under `:root` and `.dark`, generated by `shadcn init`.

### Supabase integration

Three separate client factories under `lib/supabase/`, matching the standard `@supabase/ssr` App Router pattern — do not consolidate them:
- `lib/supabase/client.ts` — browser client (`createBrowserClient`), for use in Client Components.
- `lib/supabase/server.ts` — server client (`createServerClient`) reading/writing cookies via `next/headers`, for Server Components/Actions/Route Handlers.
- `lib/supabase/middleware.ts` — `updateSession()`, called from root `middleware.ts` to refresh the auth session on every request via `supabase.auth.getUser()`.

`updateSession()` wraps `getUser()` in try/catch so the app doesn't 500 when `NEXT_PUBLIC_SUPABASE_URL`/`NEXT_PUBLIC_SUPABASE_ANON_KEY` are unset or still placeholders (`.env.local` ships with placeholder values — see `.env.local.example`). Keep that guard when touching middleware.

### ESLint config

`eslint.config.mjs` uses `@eslint/eslintrc`'s `FlatCompat` to load `next/core-web-vitals` and `next/typescript`, rather than importing `eslint-config-next`'s exports directly as a flat array. This is required because `eslint-config-next` is pinned to the legacy-format `15.x` config while the installed ESLint (9.x) expects flat config — importing `eslint-config-next/core-web-vitals` directly here will throw (`nextVitals is not iterable`). If `eslint-config-next` is ever upgraded to a version that ships native flat config, this shim can be simplified.

1. 화면이 예쁘고 완성돼 보일 것 (심사 데모용)
2. 핵심 루프가 끊기지 않을 것

## 규칙
- 새 라이브러리 추가는 먼저 물어볼 것
- UI는 무조건 shadcn/ui 컴포넌트 사용, 직접 CSS 쓰지 말 것
- 빈 화면 금지. 모든 화면에 그럴듯한 더미 데이터가 기본으로 보이게 할 것
- 한 번에 파일 3개 이상 건드리는 작업은 먼저 계획을 말할 것
- 에러 처리는 toast 한 줄이면 충분
- service_role 키는 서버 사이드에서만 사용
- 기능 하나가 완성되고 동작 확인이 끝나면 커밋 후 push까지 진행할 것
- 성능 측정이나 동작 확인 목적으로 LLM API를 반복 호출하지 말 것. 실제 호출은 사용자가 직접 수행한다. 측정이 필요하면 먼저 물어볼 것.
